# NEXUS human decision review — candidate v1

Date: 2026-11-05 Asia/Bangkok. Base commit: 1035900bba56a875ea71c25776817ab1abb3b4aa.

## Scope and status

This candidate implements the human-review foundation selected by the owner:
show evidence and a recommendation, record the user's decision, and retain its history.
Agreeing with a recommendation does not execute a block, isolate an endpoint,
kill a process, change an account, or invoke a model.

This is not a deployed detector or an approved production release.
Candidate v2 retires the Copilot UI and its routes plus the synthetic summary route.
Historical artifacts remain preserved in Git and the original source snapshot.
The v1 package and its VM validation remain preserved unchanged.
The new page is `/nexus/decision-review.html`; the new API is `/api/nexus/v1/decisions`.
The service is disabled by default and returns unavailable without creating a database.
The menu link does not activate the service.

Agent003 is the only accepted endpoint. No protected folder has been selected.
There is no new FIM configuration, collector, training, GPU use, observer restart,
observer extension, BERT cutover, build, service restart or external data transfer.

## Components

- `public/nexus/decision-review.*`: plain-text evidence, review form and history.
- `src/app/api/nexus/v1/decisions/route.ts`: opt-in, bounded same-origin endpoint.
- `src/lib/decision-review.ts`: bounded stdio call to the Python worker, without a shell.
- `server/decision_review.py`: named-reviewer authentication, strict catalog and SQLite transactions.

The runtime requires host `python3` with stdlib SQLite and scrypt support, plus Node/Next.
No new npm dependencies are introduced. The worker must be included under `server/`
in any candidate frontend release. A frontend-only standalone build that omits this
directory is insufficient. The process timeout is eight seconds; API body limit is
4096 bytes and its read deadline is three seconds. Worker output is bounded to 16 MiB.

## Identity and actions

The old shared preview login cannot identify an individual reviewer. This feature
therefore uses a separate private named-reviewer registry. No production credentials
are shipped or generated by the tests. User/account provisioning remains an operator
task requiring the owner to identify authorized reviewers.

Each registry user has a unique login and actor reference, role `viewer` or `reviewer`,
a 16-byte hex salt, and a 64-byte hex scrypt digest (N=16384, r=8, p=1).
Passwords are 16–128 characters and are never stored in browser storage, audit rows,
arguments, responses or source code. A pseudonymous actor reference is displayed;
its binding to a person must be maintained by the authorized operator.
Use the approved HTTPS access path or authenticated SSH tunnel for named credentials.
Existing shared preview credentials do not automatically grant write permission.

POST accepts only:

- `request_id`: UUID v4 idempotency key
- `alert_id`, `alert_revision`: exact server-catalog identity and revision
- `expected_seq`: last observed decision sequence for this alert, initially zero
- `action`: `investigating`, `agree_recommendation` or `no_action`
- `reason`: trimmed plain text, 1–500 characters

It does not accept browser-supplied actor identity, paths, scores, targets or execution flags.
SQLite `BEGIN IMMEDIATE` serializes competing writes. Identical retries return the same
record, changed payload/actor retries conflict, and stale sequence/revision returns 409.
Audit rows are append-only through this API and SQLite triggers reject update/delete.
These controls do not make the database tamper-proof against its host administrator.

The browser keeps an uncertain request in memory and retries its original idempotency key.
A reload/new browser session does not retain that pending key; the operator must inspect
the persisted history before submitting a new decision after an uncertain result.
The UI clears prior observations on authentication or loading failure and does not fall
back to synthetic alerts. It never calls any response execution endpoint.

## Catalog boundary: important remaining integration work

Version 1 reads an explicitly pinned, immutable, operator-approved catalog. No sample
catalog is installed or activated. Test fixtures are synthetic and used only in tests.

This is a batch review foundation, not a live DFP/ransomware feed. The remaining work
includes a trusted detector-to-catalog projection and a reviewed catalog-update lifecycle.
The SQLite store is pinned to its initial catalog; changing the environment hash alone
fails closed. Do not create a new database or drop history merely to update alerts.
A future migration/ingestion change must preserve earlier decisions and handle new
and revised alert identities explicitly before a live feed can be accepted.

Catalog contract:

- `schema_version = nexus-human-review-v1`, UTC `generated_at`,
  `automated_response_allowed = false`, at most 20 `items`.
- Each item has a digest `alert_id`, `endpoint_id = 003`,
  `pipeline = dfp | endpoint-file-behavior`, and
  `source_mode = shadow | controlled-test | replay` (no live quality claim).
- UTC `event_time` and `detected_at`; versioned `detector_id`, `detector_version`,
  and `feature_contract`; explicit coverage and validation status.
- Score semantics are pipeline-specific. DFP reconstruction error is not constrained
  to a probability; true zero is preserved. Classifier scores must be in [0,1].
- Bounded findings, limitations, and digest-only evidence references; no raw-log/path fields.
- Recommendation is `investigate` or `consider_endpoint_isolation`. The latter requires
  validated status, verified coverage and non-replay input. These are trusted catalog
  assertions, not independent proof or response authorization.
- The revision hashes all accepted item fields, including recommendation and evidence.

The catalog publisher must establish provenance, redact free text and support every
validation/coverage assertion. Field validation cannot prove semantic correctness or
detect personal information embedded in otherwise allowed text.
Do not relabel the existing FIM 12/12 transport check as ransomware accuracy.
Do not feed FIM counts into the AppShield 297-feature model. The latest owner scope
uses endpoint behavior without BlueField; the older AppShield architecture document
still needs explicit reconciliation before deployment.

## Private storage and activation: not performed by this patch

Fixed runtime root: `/mnt/nexus-copilot-mQTssj/nexus-human-review-v1`.
Root must be owned by the service user with mode 0700; its parent must be owned by that
user and not group/world writable. Files must be owned by that user, mode 0600,
regular, single-link and not symlinks. Preserve permissions in backups.

Expected files are `reviewers.json`, `catalog-<sha256>.json`, and `decisions.sqlite3`.
Registry shape is `{schema_version: nexus-reviewers-v1, users: [...]}` with user fields
`login`, `actor_ref`, `role`, `salt`, `scrypt_sha256`.
No credentials or catalog are provisioned by HTTP. `decision_review.py --initialize`
is an explicit offline administrative operation after catalog/identity acceptance;
it refuses to overwrite a database. A failed initialization is retained for review.

Do not enable until the scoped source/catalog and reviewer identity are accepted.
Activation would require `NEXUS_DECISION_REVIEW_ENABLED=1` and
`NEXUS_DECISION_CATALOG_SHA256=<approved hash>`, an initialized private store, the
worker packaged in the release, and a reviewed candidate deployment/rollback.
This patch sets none of those values and restarts nothing.

There is a limit of 100 decisions per alert and 64 MiB for the SQLite main file.
Limits fail closed; archive/retention and catalog migrations must be designed to
preserve history before expanding this candidate's workload.

## Validation

Run from frontend in an isolated candidate copy:

```bash
python3 -B tests/test_decision_review.py
node tests/decision-review.cjs
node tests/decision-review-typecheck.cjs
node tests/llm-retirement.cjs
```

Python tests use synthetic identities/catalogs and temporary SQLite files. Actual
POSIX owner/mode/no-follow checks run on Linux; those two integration tests are skipped
on Windows. Node tests mock the worker and browser DOM, including unsafe text,
uncertain retries, stale conflicts, viewer rights, unavailable sources and no execution.
The TypeScript command checks the two new modules only. Full repo typecheck/build and
real browser/HTTP acceptance remain required before a deployment decision.

No private credentials, datasets, model artifacts or source events are required by tests.
Code tests alone do not accept DFP baseline, thresholds, coverage or detection quality.
