## แผนออกแบบ development data ก่อนพิจารณาฝึก

1. คง snapshot และ hashes เดิม ตรวจ manifest/source lineage บน VM เพื่อระบุว่าแต่ละ cohort มาจาก lab, operational source, replay หรือยังไม่ทราบ แยก lab marker ออกจาก verified provenance
2. เสนอ provenance ledger ภายใน VM: cohort ID, source reference/hash, UTC interval, manager-agent grouping, authorized scenario/change record, provenance status/reviewer และ eligibility reason ไม่ส่ง raw evidence ออกภายนอก
3. ทำบัญชี protected membership เดิมของ train/validation/quarantine/reserve และตรวจ UID/hash/template overlap ก่อนคัดเลือก ไม่เปิด text หรือผล reserve เพิ่มเพื่อจูน
4. นิยาม template grouping แบบกำหนดเวอร์ชันไว้ล่วงหน้า เก็บ hash ของข้อความเดิมควบคู่ ห้ามถือว่าลบ path/time แล้วจะไม่มี leakage โดยอัตโนมัติ ใช้ template เพื่อแบ่ง/ตรวจข้อมูลก่อน ไม่แก้ v2 model input contract เงียบ ๆ
5. ออกแบบ split แยก UTC windows และ manager-agent groups พร้อมกัน จากนั้นจัด connected template/duplicate groups ให้อยู่ฝั่งเดียว ห้ามสุ่มแถวที่สัมพันธ์กันข้าม split; ถ้าแยกไม่ได้ให้รายงาน coverage ว่าไม่พอ
6. หา positive cohorts จากหลาย rules/scenarios, endpoints และ time windows ที่ยืนยันที่มาและได้รับอนุญาต พร้อม low controls จากบริบทที่เกี่ยวข้อง ไม่สร้าง label ว่าโจมตีจากชื่อ rule หรือกิจกรรม package/FIM เพียงอย่างเดียว
7. รายงานจำนวนแต่ละ cohort, missing description/full_log, truncation, label balance, template overlap และ subgroup coverage ก่อนเสนอ split manifest ไม่มีการรับประกันจำนวนขั้นต่ำหรือ quality target จาก inventory นี้
8. เมื่อทีมเห็นชอบ provenance, split และ evaluation plan แล้วจึงพิจารณาโมเดลทดลอง แยกจาก live model; freeze contract/metrics/threshold-selection policy ก่อนทดลอง และขอ GPU reservation ใหม่ก่อนรัน
